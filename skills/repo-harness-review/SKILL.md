# Repo Harness Review

按**文档、代码、测试分层、可观测性、可验证性、交付与恢复**六方面独立评价。评的是仓库当前的设计、契约和默认约束。选一个版本和代表性变更来检验设计。只对取证范围下结论。静态审查不替代新功能验收。

默认用中文报告，保留命令、路径和原始错误。只评估，除非用户另行要求实施。

## 固定评估切片

记录 repo、commit、工作区改动、检查范围和环境限制。选一条重要用户路径和一个高风险分支；用户已指定就沿用。写明要检验的设计契约和一个反例，例如 “新增协议字段，旧消费者是否能读；仓库要求拿什么证明”。不要求为当前变更执行反例。库用外部调用方，服务用 API，CLI 用进程输出及退出行为，UI 用实际可见结果。

## 维度 1：文档。代码是最好的实现文档，文字只补代码表达不好的东西

现行实现优先读代码、类型、schema 和可运行示例。公开契约描述承诺，不是实现的转述；代码违背契约，应报告差异而不是默认代码正确。抽一份入口文档、一份契约或 ADR，逐段说明它帮助谁做什么。

| 子项 | 看什么 | 怎么取证 | 反模式 |
| --- | --- | --- | --- |
| 入口与导航 | 能否快速找到主入口、模块所有者和验证方式。 | 从 README 或 agent 入口实际追到一个行为的实现与检查。 | 目录树到处复制；长篇背景挡住主入口。 |
| 上手与示例 | 只写实际需要的依赖、数据、权限，给一条能照跑的最短路径。 | 对照脚本和配置；获准时跑当前版本示例。 | 演示用了隐含本机配置；列了十条命令却没有一条完整路径。 |
| 契约与取舍 | 保留对外承诺、兼容限制、设计原因和无法从代码推断的背景。 | 抽一条承诺对照实现与契约测试；翻 ADR 看是否已被替代。 | 逐行翻译代码；把历史决定当成现行 API；为减字删除边界条件。 |
| 信息密度与去冗余 | 用删除测试：指出删除这段后，读者会失去哪项操作、约束或判断。同一事实是否只维护一个来源？ | 逐段标注「留、合并、改链接、删」，指出重复位置和保留来源。 | 空泛原则、同义复述、代码和多个 Markdown 各抄一份参数表。 |
| 保鲜机制 | 可派生事实链接到源或按需生成；示例和关键路径进入对应测试；影响行为的契约变化跟代码一起更新。 | 抽查最近一次接口或配置变化：源改后，文档是否同步，或检查是否能发现漂移？ | 只加“定期更新”提醒；链接仍有效却指向过时契约；依赖人工同步大量副本。 |

## 维度 2：代码。边界清楚，改一个行为尽量只改对的地方

| 子项 | 看什么 | 怎么取证 | 反模式 |
| --- | --- | --- | --- |
| 架构与边界 | 责任所有者、依赖方向、公开与内部边界。 | 从用户入口追到副作用，指出谁决定策略、谁只传递事实。 | SDK 擅自过滤调用方需要的原始事件；跨层读写彼此内部状态。 |
| 领域建模 | 关键概念是否有类型，状态与不变量在哪里表达。 | 选一条非法状态或转移，指出拒绝它的代码。 | 多个布尔量分散表达同一个状态；每个调用方都得记住相同前置条件。 |
| 复用与局部性 | 同一条规则是否只需改一次；抽象是否让调用方少知道实现细节。 | 选一个具体需求变化，列出必改位置，并说明是否真共享规则。 | 为省几行把变化原因不同的代码绑在一起；同一规则散落多处。 |
| 可读性 | 名字、类型、数据流和控制流能否解释行为。 | 从调用点复述主路径与关键分支，核对是否必须读大量旁路代码。 | 注释复述代码；或为追求零注释而删除协议原因和不变量。 |
| 可测试性 | 能否在合适的边界隔离或观察副作用，例如时间、进程与存储操作。 | 找能独立测试规则的入口，确认无需大改业务或连生产。 | 为每个函数创建接口；另一极端是测一个判断也要启动全系统。 |
| 失败语义 | 失败、取消、重试、部分成功和未知结果能否区分。 | 顺着一个失败走到调用方，检查错误信息、状态、副作用和重试条件。 | 用一个 error 吞掉是否已发送的信息；无条件重试非幂等操作。 |

## 维度 3：测试分层。在成本最低、证据足够的层抓住失败

不要按目录名分类。对主路径和高风险分支写清楚：要拦的回归、最合适的层、实际使用的依赖和独有证据。

| 子项 | 看什么 | 怎么取证 | 反模式 |
| --- | --- | --- | --- |
| 单元 | 本地规则、边界值、状态转移；快速、确定。 | 选一条规则，确认测试断言结果或不变量，而不是函数调用顺序。 | 测 getter、第三方行为、无业务意义的私有实现；mock 比被测代码复杂。 |
| 契约 / 集成 | 验证边界协作：外部消费、协议、序列化、事务或持久化。 | 画出真实与替换的边界；核对断言有没有穿过所声称的边界。 | 把要验证的边界也 mock 掉；只看成功返回，不看落库或协议结果。 |
| 端到端 / Live | 少量关键旅程从真实入口走通。产品端到端和真实外部 provider 参与分开报告。 | 指出真实入口、可见结果和实依赖；核对是否有当前 provider 的版本证据。 | 用浏览器覆盖每个纯逻辑分支；把本地协议回放说成真实 provider 验证。 |
| 滥用与重叠 | 每层都应拦住它特有的失败，或以合理成本提供独立保护。 | 抽两条疑似重复用例，问“移除它会失去哪类失败证据？能否下沉？” | 为覆盖率堆测试；多个层只断言同一个结果，没有额外风险收益。关键契约故意跨层复验不算滥用。 |
| 隔离与稳定 | 数据、时钟、随机性、并发、外部状态是否可控，失败是否可诊断。 | 查 fixture、清理、超时与历史 CI；把已观察到的 flaky 与推测分开。 | 共享全局状态、判断就绪靠固定 sleep、失败靠自动重试掩盖。 |
| 执行策略 | 快层、慢层和 live 层是否各有执行入口，适配提交和发布节奏。 | 从 CI 或发布配置确认触发条件，找真实运行记录及跳过条件。 | 测试存在却不跑；每次小改都跑昂贵 live；长期隔离的失败无人跟进。 |

## 维度 4：可观测性。发现并定位运行故障

只评 **日志、指标、Trace** 三项。性能指标归入指标。取一条真实或可控故障，从发现到定位；没有实跑就标明证据级别。

| 子项 | 看什么 | 怎么取证 | 反模式 |
| --- | --- | --- | --- |
| 日志 | 记录关键结果、失败原因和关联字段；噪声可控，不泄露秘密。 | 找一条故障日志，用请求或 Session 线索追到具体步骤，区分未发送、失败和结果未知。 | 只有“操作失败”；正常轮询刷屏；把 prompt、token 或原始凭据写入日志。 |
| 指标（含性能） | 按职责看成功率、失败率、活跃数、积压，以及延迟分位数、吞吐和资源用量；需要时才设告警。 | 复核采集口径、单位、维度和查询；例如能按 provider 查 Resume 的 P95，并知道量的是提交还是完整 turn。 | 只看平均延迟；把 Session ID 当标签；把由采样 span 算出的数量冒充全量指标。 |
| Trace | 一次请求里的关键步骤是否串得起来，跨度起止和传播边界是否可信。 | 按 trace ID 查一条调用，从入口追到 SDK 或 provider 边界；标出采样、异步段及 best-effort 传播。 | 有 span 却串不起来；把 SDK 提交 span 当成完整 turn；用 trace 替代 Session 原始事件。 |

访问范围、保留和敏感数据对三项都适用。日志、指标或 Trace 不适用时给理由；不以引入 OTel 或信号齐全加分。

## 维度 5：可验证性。仓库为后续变更提供的约束和能力

测试分层看既有用例如何分工。可验证性看**后续变更能否复用仓库的验证契约、入口和约束**。这里评价设计，不要求为当前功能执行验收，也不替仓库临时组装一套 harness。

| 子项 | 看什么 | 怎么取证 | 反模式 |
| --- | --- | --- | --- |
| 验收契约 | 仓库是否规定不同类型变更要证明哪些可见结果，失败和关键不变量怎么算，谁负责例外。 | 查贡献规则、PR 模板、契约、验证矩阵或项目内验证 skill；挑一类变更追到这类变更的通过标准。 | 只写“补测试、确保通过”；靠 reviewer 临场定义验收标准。 |
| 可复用验证入口 | 是否已有稳定入口能驱动相应边界，如外部 SDK 调用、CLI、API、UI、离线协议驱动或回放。 | 从贡献入口追到项目自带的 runner；标出它适用的改动和缺失的边界。 | 每次都要临时拼脚本、找真实账户或依赖某位维护者的机器。 |
| 环境与观测点 | 是否能按需获得隔离实例、可控输入、就绪信号和可检查的业务输出，且不触及生产。 | 查 fixture、临时目录、启动/清理接口和输出协议；看能否验证一个关键失败而不大改业务代码。 | 只能对共享环境操作；没有稳定方式区分“请求接受”和“业务完成”。 |
| 约束与证据归档 | 仓库是否规定何时要出具证据、以何种形式关联变更，哪些检查或人工审批必须通过。 | 把一条规则从文档或模板追到版本化脚本、工作流、要求提交的产物，分别注明有约定、可执行或强制。 | 截图无版本；CI 只编译却叫功能验证；口头说必须，实际可无记录跳过。 |

## 维度 6：交付与恢复。控制暴露范围并定义升级与退出契约

评估仓库提供的设计能力，不做单次发布复盘，也不要求实际灰度、迁移或恢复。用一个可能改变行为或数据格式的变更检验契约是否清楚。库和服务不要求同一种交付机制。

| 子项 | 看什么 | 怎么取证 | 反模式 |
| --- | --- | --- | --- |
| 灰度与暴露控制 | 是否能把部署与启用分开；能否按目标范围启用功能，默认是什么，关闭是否有效，谁能变更。 | 查 feature gate、配置、路由或 SDK 显式 opt-in 的契约与作用域。按项目风险判断是否需要按租户、实例或流量分组。 | 功能只有部署即全开；开关只藏 UI，后台仍写数据；对简单库强求百分比灰度。 |
| 版本与兼容契约 | API、协议、配置与持久化数据分别如何标版本；旧读新、新读旧、混跑或显式拒绝的边界是什么。 | 查 schema/version 字段、兼容矩阵与支持范围，明确谁读谁写、何时拒绝和如何提示。 | 只写“向后兼容”，不说明方向和版本范围；把旧数据不可读留到运行时才发现。 |
| 升级与迁移契约 | 变更顺序、迁移前置条件、写入切换与失败恢复是否明确；不支持原地升级时是否有清楚替代路径。 | 查升级规范、版本守卫与迁移入口；标出重跑、恢复点、历史数据访问和不可逆步骤。 | 二进制一换就开始不可逆写入，没有保护；只许升级却不说明旧数据怎么访问。 |
| 止损与恢复契约 | 关闭功能、回滚程序、回退配置和恢复数据分别能保证什么；何时只能前滚或从备份恢复。 | 查 kill switch、兼容窗口、数据保留与恢复契约；指出过了哪一步就不能回滚。 | 关闭开关被当成能撤销已发生的写入；把旧进程能启动当成数据可降级。 |
| 发布约束与版本溯源 | 仓库是否定义产物、源版本和必要检查的绑定，以及何时可以推进下一阶段。 | 查发布契约、流水线规则或产物元数据，不以某次发布成功代替设计能力。 | “有 CI”被当成门禁；发布物和接受检查的源码不是同一版本。 |

## 按风险追加检查，不默认新增分数

- **安全与数据边界**：有权限、外部输入、密钥或用户数据时，单列高风险缺口；不要用其他维度高分掩盖。仅做已授权的防御性检查。
- **性能与资源**：在可观测性的指标项评估性能信号。如果需要评估性能预算、负载模型或基准回归，单列专项。禁止重复计分。
- **开发与 agent 体验**：默认作为贯穿六项的视角；构建和验证环境的可重现性在文档、测试和验证中观察。不重复给分。

## 输出：六项结论和一个最小改进

每个评价面独立给等级，不合成总分。逐项报告每个子项：证据、判断和限制；缺证据标未验证，不强行打分。没有找到证据时，写明查找范围。

- **0 缺口**：明确缺失或有反证。
- **1 薄弱**：依赖约定或替代信号。
- **2 有机制**：有明确设计或机制。适用范围、接入或约束力度仍不清楚。
- **3 有证据**：设计适用范围和责任明确。当前版本能追到契约、入口或执行约束。不要求本次实跑。
- **? 未验证**：缺少证据。
- **N/A 不适用**：说明原因。

1. **范围**：版本、路径、预期行为和反例。
2. **六项结论**：给每个维度评等级，引用关键证据。
   - 标明证据类型，并为每个子项列出设计、证据和限制。
   - 区分拟议方案、已约定、已提供可用机制、已强制。
   - 一次实跑或历史 CI 结果不能证明仓库强制检查。
   - 同一份 CI 记录可支持多个事实，不按记录重复加分。
3. **附加风险**：仅列适用的安全或性能发现；无则省略。
4. **最小改进**：点名最影响交付的瓶颈，给一项优先改进及其验收。如果类型、边界或 lint 能消除同类错误，优先用这些机制。如果缺少可复跑证据，补最小检查。如果缺的是因果、取舍或导航，才补文档。不要默认建框架。

## 试跑题（未执行）

- **MASS Observer**：检查仓库是否规定改动版本预览时验证实际选中的 option ID。核对浏览器隔离入口、确定性测试数据和证据格式。无需重跑本次功能。
- **agent-sdk-go**：核对外部消费者的协议验收契约。区分回放和真实 CLI 各自验证的边界。核对旧调用方的兼容范围和新行为的启用方式。
- **MASS Core**：选一次数据格式变化作切片。核对部署和启用能否分开。标出允许读写或共存的版本。说明何时停止升级或改走恢复路径。明确拒绝旧目录并保留原数据可以是契约，不默认要求自动迁移。
